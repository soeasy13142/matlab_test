## 背景与范围

作业四提高要求第 2 条要求「运用 MATLAB 编程设计功能完善的图像处理实验平台，
实现图像管理、算法操作、参数调节、结果展示等」。

**本轮只做子项目 D（界面）**。子项目 A（算法库）+ B（验证）已完成一部分：
`+img/` 下有 4 个算法（灰度变换、阈值分割各 2 个），另外 6 类暂不实现。
C（格式兼容）、E（报告生成）不在本轮。

本文档取代上游 spec 的「后续阶段 C、D、E 的接口约定」中关于 D 的部分，
理由见下面「与上游 spec 的差异」。

## 实测事实

设计前在本机 R2025b 上实测，以下四条都推翻了「凭直觉会那么写」的做法：

| 实测 | 结果 | 影响 |
|---|---|---|
| `exist("img.grayGamma")` | **返回 0**（该函数明明存在） | 不能用 `exist` 探测包函数是否实现 |
| `exist("img.grayGamma","file")` | 同样返回 0 | 同上 |
| `which("img.grayGamma")` | 返回完整路径；对 `img.featHOG` 返回 `""` | **`which` 才是可靠的探测手段** |
| `str2func("img.featHOG")` | **成功**返回句柄（函数并不存在） | `str2func` 不能用来探测 |

界面控件：

| 实测 | 结果 | 影响 |
|---|---|---|
| `uitreenode` 属性表 | 无 `Enable`（`Text` / `NodeData` / `Children` / `Icon` 等，仅此） | **树控件做不到逐节点灰显**，只有整棵树有 `Enable` |
| `uibutton` | `Enable="off"` + `FontColor` 可设 | 用按钮实现灰显 |
| `uiaxes` + `imshow` | 正常 | 结果展示可用 |
| `uitree(...,'CheckBoxTree',...)` | 属性无法识别 | 该版本无此参数 |

性能（源照片 4284×5712 灰度图，四个算法全分辨率跑）：

| 算法 | 耗时 |
|---|---|
| `grayGamma` | 0.104 s |
| `grayLinearStretch` | 0.099 s |
| `threshOtsu` | 0.010 s |
| `threshIterative` | 0.302 s |
| 合计 | **0.514 s** |

结论：**不需要缩略图预览**，直接在全分辨率图上计算与展示。

## 与上游 spec 的差异

上游 spec 的 D 节写「算法调用统一走 `feval("img." + fcnName, I, params{:})`」。
实测 `str2func` 对不存在的函数也返回句柄，所以派发方式本身可用，但**探测必须换成 `which`**。
其它差异：上游未预见 `uitreenode` 无法逐节点灰显。

## 架构

界面沿用上游 spec 已定的**程序化 `uifigure`**，不用 App Designer 的 `.mlapp`。
理由是老问题：`.mlapp` 入库后是二进制 Zip 包，改一个控件位置整个文件重写，
git 无法 diff，与本项目「可读的 `.m`」约定冲突。作业原文写「可选用 MATLAB App
Designer 或 GUI 设计」，程序化 GUI 属于后者，合规。

### 文件结构

```
hw04-imageGeometry/platform/
├── imgPlatform.m       GUI 主入口
├── imgRegistry.m       算法登记表（纯数据 + which 探测）
├── verifyPlatform.m    登记表一致性自检
├── verifyAlgorithms.m  （已有，A+B 阶段）
├── README.md           （已有，需更新）
└── +img/               （已有 4 个算法）
```

### 单元划分

三个文件各有一个清楚的职责，可以独立理解与验证：

- **`imgRegistry()`** —— 返回 8 类 16 个算法的元数据。不碰界面，可以在命令窗口
  直接调用并打印，是界面与算法之间的唯一接口。加算法只改这里。
- **`verifyPlatform.m`** —— 只检查登记表自身是否自洽。不需要开界面。
- **`imgPlatform()`** —— 只负责搭界面、绑回调、派发算法。算法知识全部来自登记表。

## 算法登记表

`imgRegistry()` 返回一个 16×1 的 struct 数组，每项字段：

| 字段 | 含义 | 例 |
|---|---|---|
| `Category` | 类别名 | `"灰度变换"` |
| `Name` | 算法显示名 | `"伽马变换"` |
| `Fcn` | 包函数名 | `"img.grayGamma"` |
| `Params` | 参数定义 cell 数组，无参数时为 `{}` | 见下 |
| `Output` | 输出类型，决定怎么展示 | `"image"` / `"binary"` / `"vector"` |

**「实现了没有」不写死字段，用 `which(Fcn)` 现场探测**（`isempty` 为真即未实现）。
这样以后补上 `+img/featHOG.m`，界面自动点亮，登记表与界面都不用改。

### 参数定义

每个参数是一个 struct：

| 字段 | 含义 |
|---|---|
| `Name` | 参数名，与 `+img/` 里的形参名一致 |
| `Default` | 默认值 |
| `Kind` | 控件类型，见下表 |
| `Min` / `Max` | `"slider"` 与 `"size"` 用 |
| `Options` | `"choice"` 用，候选字符串数组 |

四种控件类型，每种都只有几行代码：

| `Kind` | 控件 | 用在 | 例 |
|---|---|---|---|
| `"slider"` | 滑块 + 数值框，双向同步 | 范围明确的数值 | `gamma` 0.05–3 |
| `"edit"` | 仅数值框 | 跨数量级的数值 | `tol` 1e-9–1e-2 |
| `"choice"` | 下拉 | 枚举字符串 | `method` nearest/bilinear/bicubic |
| `"size"` | 两个数值框 | 二元素尺寸 | `targetSize` [120 200] |

16 个算法的参数全部登记，签名取自上游 spec 已确认的清单。未实现的 6 类虽然
按钮是灰的、参数永远渲染不到，参数定义仍然写全 —— 这样「以后补上算法，
界面一行不用改」这句话才是真的。

已实现的 4 个：

| 算法 | 参数 | Kind | 默认 |
|---|---|---|---|
| `grayLinearStretch` | `lowIn` | slider 0–255 | 30 |
| | `highIn` | slider 0–255 | 220 |
| `grayGamma` | `gamma` | slider 0.05–3 | 0.5 |
| `threshOtsu` | （无） | | |
| `threshIterative` | `tol` | edit 1e-9–1e-2 | 1e-6 |

## 交互与错误处理

- **参数控件按算法动态生成销毁**：切换算法时清空参数区重建，旧控件 `delete`。
- **点「执行」才计算**，不做拖动实时预览。实测单次 0.1 s 虽快，但全图重绘会拖慢
  拖动手感，作业场景也不需要。
- **彩色图自动转灰度**：`+img/` 的算法开头都有 `~ismatrix(I)` 检查，彩色图直接
  报错。打开时自动 `rgb2gray` 并在顶部状态栏标注「已自动转灰度」，不弹错误框。
- **算法报错用 `uialert` 显示 `err.message`**，不静默吞掉。现有算法的错误信息
  已经写得很清楚（如「只接受二维灰度图」）。
- **未实现算法的按钮 `Enable="off"`**，点不动。
- **未载入图像时的初始状态**：4 个算法按钮与「保存结果」都是灰的，
  「执行」也点不动；打开图像后一起点亮。避免空图时点了报错。
- **结果展示按 `Output` 分派**：`"image"` / `"binary"` 走 `imshow`，
  `"vector"` 走 `plot`（当前 4 个算法都是前两类，`plot` 分支为将来留）。
- **保存结果**：保存的是**当前结果图像**（即上一次点「执行」算出来的那个矩阵），
  不是界面截图。`uiputfile` 的文件类型过滤器列出 BMP / JPG / JPEG / PNG /
  TIF / TIFF / GIF 五种格式，底层直接 `imwrite`，按扩展名选格式。这顺带覆盖了
  第 3 条的界面部分；第 3 条要求的往返无损验证仍属 C 阶段，不在本轮。
- **读图失败**（文件损坏、格式不支持）用 `uialert` 提示，界面保持原状。

## 验证方式

GUI 没法自动点击，所以拆成两层。

**自动：`verifyPlatform.m`** —— 只验登记表，不开界面，跑完打印检查项，
未通过则非零退出码（与 `verifyAlgorithms.m` 同一风格）：

1. 类别数为 8，每类恰好 2 个算法，共 16 个；
2. 每项 `Fcn` 以 `"img."` 开头；
3. 对每个**定义了 `Min`/`Max` 字段**的参数，检查默认值落在区间内；
4. `Output` 取值属于 `{"image","binary","vector"}`；
5. `Kind` 取值属于 `{"slider","edit","choice","size"}`，且 `"choice"` 必有 `Options`。

**人工：运行时操作清单** —— 交付时附一份「点哪几个按钮、改哪个参数、
该看到什么」，照着点一遍即可。

## 风险

**界面无法自动测试。** `uifigure` 的回调只能靠人点，`verifyPlatform.m` 覆盖不到
界面逻辑。对策是让界面里的算法知识全部来自登记表，界面代码只剩机械的控件搭建
与派发，出错的面积因此很小。

**大图首次渲染可能偏慢。** `imshow` 把 4284×5712 送进 `uiaxes` 的耗时未实测
（算法本身只要 0.1 s）。若实测卡顿明显，退回「显示前先 `imresize` 到千像素级，
但算法仍跑全图」—— 只影响显示，不影响结果。实施时实测确认。

## 验收标准

1. 双击或点运行 `imgPlatform.m` 能开出界面，不报错；
2. 打开一张彩色照片，自动转灰度并显示，状态栏有标注；
3. 4 个已实现算法都能选中、跑到结果、并显示耗时与尺寸；
4. 6 类未实现算法的按钮为灰、点不动；
5. 保存结果能弹出含 5 种格式的对话框并成功写文件；
6. `verifyPlatform.m` 退出码 0；
7. 每个函数有 H1 行 + 功能说明 + 输入输出 + 一个调用示例；
8. 跑通即按 `git.md` 的粒度提交。
