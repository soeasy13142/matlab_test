# 作业四 · 图像的几何运算

源照片 `photo.jpg` 是 5712×4284 的彩色 JPEG（教室内的真人照），共 24 470 208 个像素。
脚本 `hw04_process0.m` 把它读成灰度矩阵 A，再做旋转、缩放、显示与保存。

## 一、基础要求的实测结果

### 1. 四个矩阵的实际尺寸

| 矩阵 | 操作 | 尺寸（行×列） | 耗时 |
|---|---|---|---|
| A | `rgb2gray(imread(...))` | 4284 × 5712 | — |
| B | `imrotate(A, 50, "bicubic")` | 7130 × 6954 | 0.35 s |
| C | `imrotate(A, -20, "bicubic")` | 5980 × 6833 | 0.31 s |
| D | `imresize(A, [120, 200])` | 120 × 200 | 0.02 s |

耗时取 3 次重复的中位数。首次运行含函数预热，会偏高约 0.15 s，所以脚本直接打印的
那次总耗时（约 0.7 s）比这张表略大。

B、C 都比 A 大，B 的面积甚至是原图的 2.03 倍。这不是 bug，而是外接矩形变大导致的。
把 w×h 的矩形绕中心转 θ 角，新外接框的宽高是

```
W' = w·|cos θ| + h·|sin θ|
H' = h·|cos θ| + w·|sin θ|
```

代进 w = 5712、h = 4284、θ = 50°：

```
W' = 5712 × 0.6428 + 4284 × 0.7660 = 3671.60 + 3281.73 = 6953.33  → 6954
H' = 4284 × 0.6428 + 5712 × 0.7660 = 2753.70 + 4375.65 = 7129.35  → 7130
```

与 `imrotate` 实测的 7130 × 6954 逐位吻合。−20° 那组同样吻合（公式给出 5980 × 6833）。
所以尺寸变化完全由几何决定，跟插值方法无关。

末位取整用的是 `ceil` 而不是四舍五入：+50° 的 7129.35 若按 `round` 会得到 7129，
实际是 7130。两组共四个方向逐一验证过，只有 `ceil` 全部对得上。

### 2. 旋转图的黑色填充

题目提到「`imrotate` 对原图像边界之外的像素用 0 填充，显示的是黑色的背景」。脚本实测
B 的黑边占比 50.63%，C 是 40.09%。

这个数也能提前算出来：旋转只改变外接框，不改变图像本身占的面积，所以黑边占比就是

```
1 − (h·w) / (H'·W')
```

代入 +50° 得 `1 − 24470208 / 49582020 = 0.5065`，−20° 得 `1 − 24470208 / 40861340 = 0.4011`。
实测值比预测值都低了 0.02 个百分点，差在边界那一圈像素上：那里双立方插值
采样到了部分有效像素，结果是个接近 0 但非 0 的小正数，没被 `== 0` 统计进去。

### 3. 插值方法的选择

题目说旋转方法自定，并说明 `imrotate` 默认用最近邻插值。本题三处都取了 `bicubic`。

理由是最近邻只取离映射点最近的那一个源像素，旋转后目标网格与源网格不再对齐，抽取的
样本在相邻两像素之间跳变，边缘会形成明显的锯齿。双线性取周围四个像素加权，双立方取
周围十六个。用本图实测三种方法的差异（以逆时针 50° 为例，统计取值不同的像素占比）：

| 对比 | 不同像素占比 |
|---|---|
| bilinear vs nearest | 15.0% |
| bicubic vs nearest | 14.7% |
| bicubic vs bilinear | 7.1% |

也就是说，换插值方法会影响约一成半的像素，肉眼可见。代价是双立方要读写 16 个邻域
像素，此处实测 0.35 s，对单张照片完全可以接受。

脚本里插值方法抽成了顶部常量 `INTERP_METHOD`，想换回 `"nearest"` 只改这一行。

### 4. `crop` 参数

题目提到 `imrotate` 的 `crop` 可选参数会自动剪切旋转后多出的部分。本脚本没有使用它，
因为题目第 5 问要展示的正是旋转后的完整结果（含黑边）。作为对照实测了一下：

| 调用 | 输出尺寸 | 黑边占比 |
|---|---|---|
| `imrotate(A, 50, "bicubic")` | 7130 × 6954 | 50.6% |
| `imrotate(A, 50, "bicubic", "crop")` | 4284 × 5712 | 20.0% |

`crop` 把输出裁回原图大小，尺寸好看了，但代价是四角的内容被直接切掉，图上仍留 20.0%
的黑边（原图的四个角落在旋转后的有效区域内，而旋转图的四个角落在原图之外）。

## 二、研究与思考

### 1. MATLAB 图像处理还有哪些应用

课本里的几何变换、灰度变换、直方图均衡、空域频域滤波、边缘检测、阈值分割只是入门
部分。按应用领域分，MATLAB 的图像处理大致还有这些方向（以下函数均已在本机 R2025b
上确认存在）：

**图像增强与复原。** 除了 `imadjust` 和 `histeq`，还有自适应直方图均衡 `adapthisteq`，
它分块做均衡再插值拼接，对局部对比度不均的医学影像、遥感影像比全局均衡更有效。
复原方向处理的是「图像怎么变坏的」：`medfilt2` 去椒盐噪声，`wiener2` 做维纳滤波，
`deconvwnr`、`deconvlucy` 做去卷积，能从已知或估计出的点扩散函数反推模糊前的图像。
天文观测和荧光显微成像里用得很多。

**图像分割。** `graythresh` 求 Otsu 全局阈值，`multithresh` 求多阈值，`imbinarize` 二值化，
`watershed` 做分水岭分割，`activecontour` 用活动轮廓模型逼近目标边界，`imsegkmeans`
做无监督的 K 均值聚类分割，`superpixels` 先生成超像素再在超像素图上分割以降低计算量。
分割是「把像素变成目标」这一步，几乎所有识别任务的前端都是它。

**特征提取与匹配。** `detectSURFFeatures`、`detectORBFeatures` 找关键点，
`extractHOGFeatures`、`extractLBPFeatures` 提取描述子，`matchFeatures` 做描述子匹配。
配上 `vision.PointTracker` 就能做视频目标跟踪。这是图像拼接、三维重建、视觉里程计的
共同基础。

**图像配准。** `imregister`、`imregtform` 估计两幅图之间的几何变换，`imregdemons` 做
非刚性配准。医学上用来把不同时间、不同模态（CT 与 MRI）的影像对齐，遥感上用来做多
时相变化检测。

**三维视觉与相机标定。** `estimateCameraParameters` 标定内参和畸变系数，
`stereoParameters` 建立双目立体模型，`disparitySGM` 计算视差图，`reconstructScene`
由视差恢复三维点云，配合 `pointCloud`、`pcnormals` 做点云处理。工业上还常用结构光
或激光三角法做高精度三维测量。

**图像的频域与变换域处理。** `fft2` 做二维傅里叶变换用于频域滤波，`dct2` 是 JPEG 压缩
的核心变换，`wavedec2`、`dwt2` 做小波分解，用于多分辨率分析和图像压缩。

**深度学习方向。** `trainNetwork` 训练卷积网络，`semanticseg` 做语义分割，
`yolov4ObjectDetector` 做目标检测，`classify` 做图像分类。这是近十年变化最大的一块，
特征由网络自己学，不再需要人工设计。

**具体行业**里，医学影像用 `dicomread`、`dicominfo` 读写 DICOM 格式，配合 Medical
Imaging Toolbox 做三维重建和病灶分割（定量测体积、测灌注）；遥感影像做多光谱分类、
地物识别、变化检测；工业视觉做表面缺陷检测、尺寸测量、条码识别；交通领域做车牌识别、
车流量统计、违章检测。

### 2. 手写数字识别与车牌识别的处理流程

**手写数字识别**（MNIST 一类的任务）流程分四步。

第一步是预处理。扫描或拍摄得到的数字图像往往有噪声、倾斜和笔画粗细不均，先做二值化
（`imbinarize` + `graythresh`）分离笔画与背景，再用 `imopen`、`imclose` 等形态学操作
去掉孤立噪点和填补笔画断裂。

第二步是字符分割。整幅图上可能有多个数字，要先用连通域分析（`bwlabel` + `regionprops`）
把它们切开，再对每个字符单独处理。

第三步是归一化。把每个字符裁剪到最小外接矩形，再缩放为统一尺寸（例如 28×28），消除
书写大小和位置带来的差异。这一步的关键是保持长宽比，否则 1 和 7 会被拉成同一个形状。

第四步是分类。传统做法是提取 HOG 或 LBP 特征再送进分类器；现在更常见的是直接送进
卷积神经网络训练端到端分类。MNIST 上手写数字的识别率可以做到 99% 以上，难点从来不在
单个字符，而在于真实场景里的倾斜、粘连和书写风格差异。

**车牌识别**的流程更长，因为要先从整幅图里找到车牌。

第一步是定位。车牌在图像里表现为一块边缘密集、水平方向梯度强、长宽比接近 3:1 的区域。
做法是转灰度、用 Sobel 或 Canny 求边缘、做形态学闭运算把字符连成整块，再按长宽比和
面积筛出候选区域。中国车牌的底色（蓝底白字、黄底黑字、绿底黑字）也可以直接用来做
颜色分割辅助定位。

第二步是校正。拍摄角度会让车牌产生透视变形，用仿射或投影变换把车牌校正成标准矩形，
这一步直接决定后续识别率。

第三步是字符分割。在车牌区域内做垂直投影，投影值低谷的位置就是字符之间的间隙，按
谷值切分。中国车牌第一个是汉字（省份简称），后面是字母和数字。

第四步是字符识别。汉字部分通常需要单独训练模型，因为类别多、样本少。字母数字部分
和手写数字识别类似。最后按车牌编码规则（省份简称取合法集合、字母数字位数固定）做
一次校验，把明显不合法的结果丢弃或重识别。

两类任务共通的道理是：识别精度的大头不在分类器上，而在分割和校正这两步。分割错了，
再强的分类器也救不回来。

## 三、平台界面

提高要求第 2 条要求「设计功能完善的图像处理实验平台，实现图像管理、算法操作、
参数调节、结果展示」。界面在 `platform/imgPlatform.m`，在编辑器里点运行即开。

### 1. 界面构成

单窗口，`uigridlayout` 分两栏。左栏是可滚动的算法列表，按 8 个类别列出 16 个
算法；右栏上方是原图与结果并排两个 `uiaxes`，中间是参数区，下方一行结果信息。
顶栏放「打开图像」「保存结果」与状态栏。窗口标题带学号署名。

**用程序化 `uifigure` 而不是 App Designer 的 `.mlapp`。** `.mlapp` 入库后是个
二进制 Zip 包，改一个控件位置整个文件重写，git 无法 diff、冲突无法合并。
作业原文写「可视化交互界面可选用 MATLAB App Designer 或 GUI 设计」，
程序化 GUI 属于后者，合规。

### 2. 登记表驱动

界面不硬编码任何算法知识，全部来自 `imgRegistry.m` 的 16 条登记项：
类别、显示名、包函数名、参数定义、输出类型。

**「某个算法实现了没有」不写死在表里，用 `which(Fcn)` 现场探测。** 这条是实测
逼出来的：`exist("img.grayGamma")` 对一个明明存在的包函数**返回 0**，
`exist(..., "file")` 也是 0，只有 `which` 返回路径、不存在时返回空串。
另外 `str2func("img.featHOG")` 对不存在的函数也**会成功**返回句柄，
所以它也不能用来探测（但可以放心用来派发）。

好处是以后补上 `+img/featHOG.m`，界面按钮自动从灰变黑，`imgRegistry.m` 与
`imgPlatform.m` 都不用改。

### 3. 两个被实测推翻的做法

**没用 `uitree`。** 树控件看起来最适合列算法，但实测 `uitreenode` 的属性表里
**根本没有 `Enable`**（只有 `Text` / `NodeData` / `Children` / `Icon` 等），
只有整棵树有 `Enable`。也就是说树做不到逐节点灰显，只能要么全亮要么全灰。
改用「类别标签 + 按钮」的绝对定位布局，每个按钮单独置灰。

**滚动面板里的子控件用绝对定位，不用 `uigridlayout`。** 实测：在
`Scrollable="on"` 的 `uipanel` 里放一个固定行高的 `uigridlayout`，
布局落地后内层 grid 的高度**恒等于面板内高**（实测 678 px），不随内容增长 ——
内容涨到 40 行、需要 1046 px 时它仍然是 678 px，超出的部分被直接裁掉，
滚动条够不到。改用绝对定位后，子控件自己的 `Position` 决定内容总高，
面板才能按这个高度滚动。

顺带一提，当前 8 类 16 个算法在默认窗口（1100 × 720）下，内容总高
595 px（16 个按钮 + 8 个类别标签）小于面板内高 657 px，**放得下、不会触发滚动**。
用绝对定位是为了窗口变矮或以后加算法时能正常滚动，不是现在就需要它。

### 4. 双向同步与闭包

参数区里滑块与数值框双向同步。两个前提都实测确认过：

- 程序化赋 `uislider.Value` **不会**再触发 `ValueChangedFcn`，
  所以互相赋值不会死循环；
- 读控件值的 getter 与同步回调都用**工厂函数**造，把控件句柄作为参数传进去。
  直接在 `for` 循环里写 `@() sld.Value`，所有句柄会共享循环变量最终的值，
  取哪个参数的值都变成最后一个。实测工厂函数写法下三个 getter 分别返回
  10 / 20 / 30，直接闭包则全返回 30。

### 5. 运行时操作清单

在编辑器里打开 `platform/imgPlatform.m` 点运行，然后：

1. **看初始状态。** 左栏 8 个类别 16 个算法：灰度变换与阈值分割下的 4 个是黑字，
   其余 6 类 12 个是灰字且点不动。参数区显示「请在左侧选择一个算法」，
   「执行」与「保存结果」都是灰的。
2. **打开图像。** 点「打开图像」选 `hw04-imageGeometry/photo.jpg`。
   原图区显示灰度照片，状态栏出现 `photo.jpg   4284×5712   uint8   已自动转灰度`，
   4 个已实现算法的按钮从灰变黑。
   照片是彩色的，而 `+img/` 里的算法开头都有 `~ismatrix(I)` 检查、彩色图会直接
   报错，所以界面统一先 `rgb2gray` 并在状态栏标注。
3. **选算法。** 点「伽马变换」，参数区出现 `gamma` 一行：滑块范围 0.05–3，
   当前值 0.50，右边数值框同步显示 0.50。
4. **调参数。** 拖滑块，数值框跟着变；反过来在数值框输入 1.5 回车，滑块跟着跳。
5. **执行。** 点「执行」，结果区出现提亮后的图，信息行显示尺寸、类型与耗时
   （实测约 0.10 s）。
6. **换个算法。** 点「Otsu」，参数区变成「该算法无可调参数」（它没有入参），
   执行后得到二值图，信息行里类型是 `logical`，末尾还有一段 `阈值 0.5255`。
   换个「迭代法」再跑，末尾应是 `阈值 0.5278` —— 两个算法在这张照片上给出的
   阈值很接近，互相印证。
7. **看报错会不会被吞。** 点「线性拉伸」，把 `lowIn` 拖到 200、`highIn` 拖到 100
   （低界高于高界），点「执行」。应弹出消息框，正文含
   `highIn(100) 必须大于 lowIn(200)，否则拉伸区间为空。` ——
   这是算法自己 `error` 抛的，界面只负责原样显示，不能吞掉。
   把 `lowIn` 拖回 30 再执行一次即恢复正常。
8. **保存结果。** 点「保存结果」，对话框的文件类型下拉里有 BMP / JPEG / PNG /
   TIFF / GIF 五种格式，存成 PNG 后状态栏显示保存路径。

### 6. 三支验证脚本各管一段

| 脚本 | 管什么 | 怎么跑 |
|---|---|---|
| `verifyAlgorithms.m` | 手写算法与工具箱的输出是否一致 | 自动，退出码 0 |
| `verifyPlatform.m` | 登记表是否自洽：8 类 × 2 无缺漏、`Fcn` 前缀、参数默认值不越界、`Kind` 与 `Output` 取值合法 | 自动，退出码 0 |
| `verifyPlatformGui.m` | 界面结构：窗口数、16 个算法按钮与登记表名称一致、未载图时全部置灰 | 自动，退出码 0 |

`verifyPlatformGui.m` 是程序化构造界面再清点控件的冒烟测试，所以界面「搭得对不对」
也有自动门禁，不是全靠人看。它靠 `findall` 找控件 —— 实测 `findall` 能穿进可滚动
面板，但**只到第 4 层**，参数行里的标签在第 5 层够不着，所以断言只覆盖按钮层。

剩下真正要人眼的部分（图像显示效果、拖动滑块的手感、报错弹窗内容、
保存对话框的格式列表）靠上面第 5 节那份清单过一遍。
