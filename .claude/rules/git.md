# Git 提交规范

本项目是**单人本地仓库**，没有 remote。所以不需要分支策略、PR、code review —— 这份文件只规定**提交**本身。

<!-- 无 paths frontmatter = 每次会话都加载（官方机制）。git 规范在提交时才用得上，
     但它不绑定任何文件路径，无法用 paths 限定，因此保持无条件加载。 -->

## 核心：提交粒度要细

作业的本质是**迭代试错**：写 → 跑 → 报错 → 改 → 再跑。
所以最有价值的提交边界不是"做完了一个作业"，而是"**这个状态我验证过是对的**"。

### 以「跑通」为提交单位

脚本能跑出预期结果（`matlab -batch` 退出码 0）时，提交一次。

选这个作为边界，是因为它**客观可验证**，不靠感觉：

```bash
# 提交前确认它现在能跑；退出码 0 才提交
"$MATLAB" -batch "run('scripts/homework1.m')"
```

### 一个逻辑变化一次提交

一个基础作业通常应该是 **2–5 次提交**，而不是 1 次。典型节奏：

| 次序 | 提交内容 |
|---|---|
| 1 | 脚本骨架 + 输入输出注释（先能跑起来，哪怕结果还是错的） |
| 2 | 核心计算跑通，结果对得上手算或参考答案 |
| 3 | 处理边界情况：空输入、除零、维度不匹配 |
| 4 | 加上绘图 / 格式化输出 |
| 5 | 修正审题理解错误（最常见的返工来源） |

### 改一个能跑的版本之前，先提交

要动已经跑通的代码之前，**先把它提交掉**。这样改崩了能精确回到那个版本，而不是重写整个作业。

```bash
git restore scripts/homework1.m    # 放弃工作区修改，回到上次提交
```

这条和 CLAUDE.md 铁律第一条（改已有文件前先问我）是**配套**的：那条规则是软的，官方说明确写了 rules / CLAUDE.md 没有严格生效的保证；git 是它的硬兜底。

## 不要做的

- **不要攒着** —— 一天的改动堆成一次提交，等于没有历史。
- **不要为提交而提交** —— 改错别字、调缩进不值得单独一次。"细"指每个逻辑变化，不是每次敲键盘。
- **不要提交没跑过的代码** —— 提交前跑一遍。跑不通但确实要存的状态，用 `wip:` 前缀标明。
- **不要提交生成物** —— `.asv`、`slprj/`、`codegen/` 等已在 `.gitignore` 中，不要用 `git add -f` 强行加进来。

## commit message 格式

```
<类型>: <中文描述>
```

类型用这几个就够：

| 类型 | 用在 |
|---|---|
| `feat` | 新增功能，或新增一次作业 |
| `fix` | 修正错误（结果算错、报错、审题理解错） |
| `refactor` | 重写实现但行为不变（例如把 for 循环改成向量化） |
| `docs` | 只动注释、帮助文本、CLAUDE.md |
| `wip` | 跑不通的中间状态，临时存档 |
| `chore` | 仓库杂务：改 .gitignore、调整目录结构 |

描述说清**改了什么**，必要时补上**为什么**：

```
feat: 完成作业 2 的矩阵求逆，含奇异矩阵检查
fix: 修正二次方程判别式为负时直接报错的问题，改为返回复数解
refactor: 把逐元素循环改成向量化，结果不变
wip: 绘图部分还没调好，先把能跑的计算存一下
```

反面例子 —— 这些等于没写：

```
更新
改了一下
提交
```
